# M1 · The web must breathe

**Scale:** vacuum — §2.8's true-black regime applies. No lift, blacks at 0.
**Modules:** `cosmic.js`, `nbody.js`, `post.js`, `cosmology.js`
**Flag:** `?m1=1`, default-off (§7.4). Flipping the default is a separate commit.

The opening scale is the first frame anyone sees. §M1's complaint is that its
palette is decoration rather than physics: hue comes from `sin(uTime·0.045)`,
twinkle from `sin(uTime·(0.4 + hash))`, and the tracers are round dots, so
filaments read as fog.

Everything below replaces a sine with a quantity the simulation already knows.

---

## 1 · What §M1 asks, and the shape of each answer

| §M1 asks | Answer |
|---|---|

| Shimmer from the **growth factor D(a)**, never a bare sine | Phase advances on `ln D` and `ln a`, both integrals of the Friedmann equation, §4 |
| **Screen-space anisotropic kernel** so filaments read as thread | 2×2 eigen-decomposition of the projected tensor, §3 |
| **Continuous slow `a`-drift**; scrubbing on the deep-time lever | Stop freezing at `a = 1`; drift into the future, §4 |
| **Ordered dither**, ±0.5/255 | A final pass in `post.js`, after sRGB, §5 |

## 2 · Density and divergence from one tensor

This is the whole milestone in one idea, so it is worth deriving rather than
asserting.

The displacement field is a sum of plane waves — the same one the CPU mirrors
in `delta()` and the N-body code uses for initial conditions:

```
ψ_i(q) = Σ_m A_m k̂_{m,i} sin(θ_m),        θ_m = k_m·q + φ_m
```

Its gradient is the **deformation tensor**, and it is symmetric:

```
M_ij = ∂ψ_i/∂q_j = Σ_m A_m k_m k̂_{m,i} k̂_{m,j} cos(θ_m)
```

Note `tr(M) = Σ_m A_m k_m cos(θ_m)` — *exactly* the `div` the current shader
already accumulates. The tensor is a strict superset of what is there now, so
nothing about the existing density readout changes meaning.

Write `B = I + D·M`. Then Zel'dovich gives both quantities exactly:

**Density** — mass conservation, exact until shell crossing:

```
1 + δ = 1 / det(B)
```

**Velocity divergence** — peculiar velocity is `v = a H f D ψ`, so

```
θ ≡ ∇_x·v = a H f D · tr(M B⁻¹)
```

and since `M = (B − I)/D`,

```
tr(M B⁻¹) = (3 − tr(B⁻¹)) / D        →        θ = a H f · (3 − I₂(B)/det B)
```

using `tr(B⁻¹) = I₂(B)/det(B)`, with `I₂` the sum of principal 2×2 minors. **The
growth factor cancels.** Divergence costs a determinant and three minors on a
tensor we are already accumulating — no second pass, no velocity texture.

Sanity check in the linear limit: as `D → 0`, `3 − I₂/det → D·tr(M)`, so
`θ → a H f D tr(M) = −a H f δ_lin`. Overdensity means converging flow. That is
the correct sign, and it is why the colouring reads the way §M1 wants:

- `θ < 0` — **infall**, converging: filaments and the skin of halos → **cool**
- `θ > 0` — **outflow**, expanding: void interiors → **warm**
- `θ ≈ 0` at high `δ` — **virialized**: node cores, neither collapsing nor
  expanding → **neutral, brightest**

Luminance carries density; hue carries divergence. A void is dim and warm
because it is genuinely emptying; a node core is white because it has genuinely
stopped falling. That is §M1's *"palette is a readout of real dynamics"* taken
literally, and it is the shape of gate (b)'s four hue families.

**Shell crossing.** `det(B)` passes through zero when a fluid element collapses,
and Zel'dovich stops being valid there. Rather than hide it, use it: `det B ≤ 0`
means *this element has collapsed*, which is exactly the filament and halo
skeleton. Density clamps to a finite maximum, and the flag becomes a legibility
signal in its own right.

### The N-body path

The tensor is a linear-theory object; the PM code has no analytic ψ. It does
have a density field, so use the **continuity equation** instead:

```
∂δ/∂t + ∇·[(1+δ)v] = 0     →     θ ≈ −(∂δ/∂t)/(1+δ)
```

which is one finite difference of the density texture between substeps. This
costs one extra render target and one extra texel fetch — the density field is
already computed every substep for the Poisson solve, so the time derivative is
very nearly free.

It also earns gate (c) directly. In a virialized halo the density stops
growing, so `θ → 0` and the core goes neutral — while Zel'dovich, which cannot
virialize, keeps streaming inward and stays cool. **Pressing `N` will show the
halos change colour**, which is a far more legible statement of "gravity did
something linear theory cannot" than a slight change in dot positions.

## 3 · The anisotropic kernel

§M1 wants filaments to read as *thread, not fog*. The thread direction is a
property of the same tensor: a filament is where two axes have collapsed and
one has not, so it runs along the eigenvector of the **largest** eigenvalue of
`M` (least compression).

Doing a 3×3 eigen-decomposition per vertex would be absurd. We do not need one
— the kernel is screen-space, so project first and decompose in 2D, where the
closed form is three instructions:

```
project:   a = r₀·M·r₀,  b = r₀·M·r₁,  c = r₁·M·r₁      (r₀, r₁ = view rows)
axis:      φ = ½·atan2(2b, a − c)
strength:  (λ₊ − λ₋) / (|λ₊| + |λ₋| + ε)
```

The fragment shader then evaluates an anisotropic Gaussian in that frame. Two
things must hold or the density readout is corrupted:

- `gl_PointSize` grows by the elongation factor, or the sprite clips;
- **total energy is conserved** — brightness divides by the area scale, so a
  stretched tracer is dimmer per pixel, not a brighter blob. Otherwise
  anisotropy would masquerade as density.

For the N-body path there is no tensor, but there is a density field: the
thread runs **along the ridge**, perpendicular to the projected density
gradient. Six texel fetches, same kernel, same energy rule.

## 4 · Shimmer, and never freezing

Every `sin(uTime·…)` in both fragment shaders goes. Phase advances instead on
two quantities that integrate rather than oscillate:

- `ln D(a)` — the growth factor, integrated from the Friedmann equation;
- `ln a` — deep time itself.

Neither has a period, so no capture of any length can show a loop. The
amplitude scales with the **growth rate** `f = dlnD/dlna`, so the web shimmers
hardest while structure is actually forming and calms as Λ takes over. That is
not a stylistic choice; it is what the universe does.

Which leaves the freeze. `cosmic.js` currently sets `playing = false` at
`a = 1`, and a frozen field cannot satisfy *"continuous slow a-drift."* After
the present day the clock keeps running into the future at a reduced rate.

That needs headroom in the cosmology tables, which stop at `a = 1.5`. Extending
`A_MAX` to 8 (≈ 20 Gyr hence) is a change to a module the whole app reads, so
it carries a numeric regression test: `D(1) = 1` exactly, and `growth`, `age`
and `z` unchanged across `a ∈ [10⁻³, 1.5]` to within 1e-6. `N_TAB` rises to
4096 so the wider range does not cost resolution in the range that already
mattered.

`Space` still pauses. Scrubbing still works. The difference is that letting it
run no longer ends in a still frame.

## 5 · The dither, and the black it must not lift

§M1 adopts the reference's ordered dither at ±0.5/255, *"post-sRGB"*, because a
smooth gradient must never band and the cosmic web is the worst banding case in
the project. `post.js` ends on `OutputPass`, which does tonemap and sRGB
encode, so the dither is a new final pass after it.

There is a real collision here, and it is worth naming rather than discovering
later. §2.8 says vacuum renders to true `#000` and **blacks are never lifted**.
A naïve ±0.5/255 dither applied to a pixel at exactly zero rounds half of those
pixels up to 1/255 — the deep field stops being black.

Resolution: the dither amplitude is gated by a `smoothstep(0, 1.5/255, luma)`.
True black stays exactly black; the first visible step above it — which is
where banding actually lives — is dithered normally. Both constraints hold, and
neither is a compromise.

## 6 · Cost, and how it is paid

§5's rule: *any change that costs frames must pay for them.*

**The payment comes first.** The current vertex shader calls `length(k)` inside
the 64-mode loop — **64 square roots per vertex, per frame**, on 314k vertices,
recomputing a constant. Precomputing `k̂` and `|k|` on the CPU and packing them
as `vec4(k̂, |k|)` removes all of them, and costs no extra uniform slots: the
existing `uK` (vec3) plus `uAP` (vec2) already occupy two arrays, and the new
layout is `vec4` plus `vec2`.

**The spend.** Six tensor accumulators, `+6 mul +6 add` per mode. Then, once per
vertex, a determinant, three minors, three quadratic forms, and one `atan2`.

Roughly, per mode: −1 `sqrt`, −1 divide, +12 ALU. Per vertex: ~40 ALU added
outside the loop. Expected to land near neutral, and the bench measures it
rather than the plan guessing — `?bench=1` reports the cosmic station
separately, so the before/after is a direct read on one number.

If it lands red, the fallback is a mode-count reduction on the tensor only —
the tensor converges faster than the displacement, so accumulating it over the
first 32 modes and the displacement over all 64 is a legitimate, documentable
approximation. Not needed until measured.

## 7 · Risks

| Risk | Mitigation |
|---|---|
| `det(B) → 0` at shell crossing produces `inf`/`NaN`, and §11 warns a single NaN texel survives the bloom pyramid as a solid block | Clamp the denominator, and firewall the bright pass. §11 says do it at *both* ends; the dither pass is the second firewall. |
| Extending `A_MAX` shifts `growth()` for existing seeds, changing every galaxy | Numeric regression test before the change lands: `D(1) = 1` and the whole `a ≤ 1.5` range within 1e-6. `galaxy.js` reads `growth()` and would show any drift as different galaxies. |
| The tensor and the shader disagree — §2.7's parity trap in a new place | CPU reference implementation of `M`, `det B`, `I₂` validated against a GPU readback before the shader enters the render loop (§7.3). |
| Anisotropy read as density | Energy normalisation, called out in §3 and checked in the capture: a still with elongated tracers must have the same total luminance as one without. |
| Dither lifts vacuum black, violating §2.8 | Luma-gated amplitude, §5. Verified by sampling the deep field of a capture for any pixel in `(0, 1/255)`. |
| Four hue families do not separate at 8-bit | Gate (b) is measured, not eyeballed: histogram the capture in hue and check luminance bounds. |

**Rollback.** Everything lands behind `?m1=1`. Without the flag both shaders
take their current path, `post.js` adds no pass, and `cosmic.js` freezes at
`a = 1` as it does today. The one unflagged change is `cosmology.js`'s table
range, which is covered by its own regression test and is invisible below
`a = 1.5`.

## 8 · Gate (§M1), and how each clause is measured

| Clause | Measurement |
|---|---|
| (a) 20 s capture shows continuous motion, no perceptible loop | Frame-differenced capture over 20 s; and by construction, phases advance on `ln D`/`ln a`, which have no period |
| (b) ≥4 distinguishable hue families, all within 0.02–0.85 luminance | Hue histogram of the capture; count modes; check every mode's luminance range |
| (c) `N` toggle makes the difference *more* legible | Same frame, both modes, differenced — the halo cores must change hue, not merely position |

| (e) budgets unchanged | `?bench=1` cosmic station, before and after |

Gate (e) is the one that can fail on merit. (a) and (d) are structural.

**Clause (e) is closed — green, on an RTX 3060 Laptop at 1440p**, the first
honest budget measurement this project has taken. §5's desktop row asks for
p95 ≥ 60 fps, p99 ≥ 50, ≤ 900 draws, ≤ 2.2 M triangles, ≤ 400 MB:

| | measured | budget | margin |
|---|---|---|---|
| fps p50 / p95 / p99 | 1428.6 / **344.8** / **285.7** | ≥ 60 / ≥ 50 | 5.7× · 5.7× |

## 9 · Result, and one escalation

`node tools/gate.js --milestone M1` scores the measurable clauses at a = 0.45,
on the particle-mesh path a visitor actually gets — not the linear fallback,
which by a ≈ 0.85 has piled everything into one hue because linear theory
cannot virialize.

| Clause | Result |
|---|---|
| (a) continuous motion, no loop | **pass** — 99.9% then 80.0% of pixels change across successive intervals; start-vs-end differs by 99.9%, which a loop would collapse |
| (a) deep time does not freeze | **pass** — reaches a = 1.36 (z = −0.26) and is still advancing |
| (b) luminance band 0.02–0.85 | **pass** — p01..p99 = 0.024..0.498 |
| (b) ≥4 hue families | **FAIL — 2** (see below) |
| (c) the `N` toggle is more legible | **pass** — the hue distribution shifts 82.3% between modes, against 43.2% before |
| (d) no banding at 8-bit | **pass** — longest identical-value run 4 px, against 8 px before |
| §2.8 vacuum blacks | **pass** — 0.000% of pixels lifted to 1/255 |

Three things found by measuring rather than by looking, each a real defect:

1. **A missing factor of `a`.** Continuity in comoving coordinates carries a
   1/a on the divergence term. Dropped, it pinned the entire sky to maximum
   infall. Caught because the hue histogram was a single spike, and confirmed
   by the linear-limit cross-check now written into `thetaScale`'s docstring.
2. **Double-counting density.** Every tracer carries equal mass, so crowding
   already encodes density; scaling each tracer's brightness by density too is
   harmless while the field is linear and ruinous afterwards — at a ≈ 0.7 a
   quarter of elements have shell-crossed, so a quarter of the sky pinned to
   maximum brightness and the web washed out to a white sheet.
3. **A divergence baseline of one substep.** Δa ≈ 0.006 is a very short lever
   against a field with about one particle per cell. Replaced with a one-pole
   low-pass whose lag is ~16 substeps, which is what took clause (c) from 62%
   to 82%.

### The blocking axis: four hue families

§7.6 allows five iterations and then requires a written account rather than a
silent loop. This is that account.

**What is true.** Rendering θ on its own shows exactly what §M1 asks for: cold
infall running along the filaments, warm outflow filling the voids between
them, coherent and correct. The physics is right, and `tools/verify.js` proves
the arithmetic independently.

**What fails.** In the composited frame, 84% of lit pixels land between 240°
and 260°. Five things were tried: a two-colour lerp, unit-luminance hue
rotation, a four-stop monotone ramp, a compressed density→luminance range
(15× rather than 95×), and the low-pass baseline. Each improved something
measurable; none moved the family count past two.

**Why, most likely.** The scale draws 262k additively-blended tracers through a
3-D box. Every pixel integrates a line of sight through voids *and* filaments,
and an additive sum of differing hues is a mass-weighted mean hue. Hue
variation that is not coherent *along the ray* averages out before it reaches
the frame — which is also why the previous shader's hue spread looked wider: it
came from `sin(uTime + vQ.y)`, a wave coherent across the whole box, and §M1's
first instruction is to delete exactly that.

So this may be a genuine tension between two clauses of the same gate: colour
*honestly* by a local field, and show four hue families in a projection that
averages local fields. Three ways out, none of which should be picked by an
agent mid-milestone:

1. **Render a slab rather than the full box** — restricts each ray to one
   structure, so local hue survives. Changes what the scale *is*.
2. **Depth-sorted or occluding tracers** instead of pure additive blending, so
   the nearest structure wins the pixel rather than the sum. A real renderer
   change with a real frame cost, and §5 says add the LOD before the feature.
3. **Read the clause as "four families present and identifiable"** rather than
   "four peaks in a pixel histogram." Violet, blue, teal, amber and cream are
   all on screen and all selected by physics; the histogram merges them because
   projection does.

My recommendation is (1) as an experiment behind its own flag, because it is
the only one that fixes the cause rather than the measurement. But it changes
the scale's identity, so it is a human's call.

**Everything else in M1 is done and passing.** The flag stays default-off until
this is resolved (§7.4), so nothing here is load-bearing yet.

## 10 · The slab, and what it actually fixed

`?slab=1` renders a view-aligned slice through the box — option (1) from §9,
built behind its own flag as recommended. The slice is centred on the box and
turns with the camera, so orbiting sweeps it through the volume rather than
swinging a fixed plane edge-on, and its edge is a smoothstep rather than a cut
because a hard clip would pop tracers as the camera moves (§2.5).

It did not fix the clause it was built for. It fixed a different one, and that
turns out to matter more.

| | full box | slab |
|---|---|---|
| hue families | 2 | **2** — unchanged |
| pixels at exactly `#000` | **0.0%** | **31.7%** |
| longest identical-value run | 8 px | 5 px |
| luminance p01..p99 | 0.024..0.498 | 0.020..0.361 |

**The full-box render never reaches true black.** 262k additively-blended
tracers, integrated through the whole depth and then bloomed, leave no pixel at
zero anywhere in frame. §2.8 is not a preference — *"in vacuum the background
is true `#000` and blacks are never lifted"* — and the cosmic web has been
quietly violating it. The slab restores it, because a ray that crosses one
structure instead of twenty has somewhere to be empty.

That also makes the dither claim testable rather than argued. `?dither=0`
renders the same frame with the pass removed, and the two pure-black counts are
**identical to the pixel**: 31.7% either way. The luma gate in `post.js` was
always structurally sound, but this is a measurement instead of a paragraph.

Two measurement bugs in `tools/gate.js` were found and fixed while doing this,
which is worth recording because both produced *false failures*:

- the luminance band compared against histogram-bucketed values, so a frame
  whose dimmest lit pixel sat exactly on the 0.02 cut reported 0.0196;
- the §2.8 clause counted pixels at 1/255, which cannot distinguish a lifted
  black from a faint outer glow that legitimately quantises there. It now
  measures what the invariant actually claims — that the vacuum reaches zero —
  against the dither-off control.

**Where the hue clause stands.** With the slab the histogram does widen —
warm appears at 20° and teal at 190–220° where before there was nothing below
220° — but no second family clears 1.5% of lit pixels. The remaining
concentration is 41% at 269°, the ramp's hard-infall violet, which says the
normalised divergence is still saturating negative for most tracers rather than
spreading across the ramp. That is a calibration question with a measurable
answer, and it is the next thing to try — but it is a *sixth* iteration on one
axis, and §7.6 says to stop and say so rather than keep going. So: said.

The slab is worth keeping regardless of how that resolves, on the strength of
§2.8 alone.

## 11 · The calibration, and where the hue clause finally lands

§9's escalation asked for a human decision. It arrived, delegated back with
"choose the best option" — so the iteration counter resets and this is the
attempt that decision bought.

### What the measurement said

The §10 diagnosis was that the normalised divergence was saturating negative
rather than spreading. It was, and `zeldovich.js` could say so exactly, on the
CPU, without a browser. Sampling the *mass-weighted* distribution — Lagrangian
q, which is what the tracers actually are — at D = 0.52:

| | p01 | p10 | p50 | p90 | p99 |
|---|---|---|---|---|---|
| θ/(aHf·D) | −57.9 | −7.36 | −0.79 | +1.14 | +1.99 |

The tail is the whole story. Outflow is bounded — a void can only empty so
fast — while infall runs away as an element collapses, so the negative side is
six times the length of the positive one and then some. Under the old linear
`/2.2`, **31.9% of tracers clamped to −1**, which is precisely the 41% of lit
pixels the frame was putting inside one 10° bucket.

No linear scale can spread that. Divide by enough to keep the tail and the
middle collapses; divide by little and a third of the sky pins.

### What replaced it

A signed-log transfer — `sign(x)·log(1+|x|)·0.3899`, referenced to |x| = 12,
near the 1st percentile. Still strictly monotone in θ, so the readout is
unchanged in what it *means*; it simply carries a long tail into a bounded
range without a clamp. §9.6 makes the same argument for the sky: derive the
stops through a fixed transfer rather than choosing them by eye.

Clamping fell from 31.9% to 8.8%. The ramp stops moved onto the compressed
distribution's own quantiles rather than a notional [−1, 1] — the amber end had
been sitting at th ≥ 0.65, which nothing ever reached.

### What it bought, and what it did not

| clause | before | after |
|---|---|---|
| (c) `N` toggle legibility | 50.7% | **95.7%** |
| §2.8 pixels at true `#000` | 31.7% | **49.9%** |
| (b) hue families | 2 | **2** |

Three clauses improved sharply. The blocked one did not move at all: the peak
migrated from 269° to 210° and got *narrower* — 53% of lit pixels in a single
bucket, plus 31% achromatic.

### The conclusion, which is not a calibration conclusion

The distribution of `th` is now demonstrably spread — p05 −1.01 to p95 +0.36,
under 9% clamped. The distribution of rendered *hue* is not. Those two
statements can only both be true if the spread is being destroyed between the
tracer and the pixel, and there is only one thing in that path: **262k
additively-blended points, integrated along a ray.** An additive sum of
differing hues is a mass-weighted mean hue, and the slab shortened that ray
without eliminating it.

So the §9 hypothesis was right, and the calibration — which was a real defect,
and worth fixing on the strength of what else it fixed — was never going to be
the answer to this clause.

**What is left is §9's option (2): stop compositing tracers additively**, so
the nearest structure wins a pixel instead of the sum of everything behind it.
That is a renderer change with a real frame cost, §5 says add the LOD before
the feature, and nobody knows this project's frame cost yet because the GPU run
has not happened. It should wait for that number.

Eight iterations have now gone at this axis. The physics is right, the transfer
is right, the palette is right, and the compositor is wrong. That is a
different milestone's problem to solve, and saying so is cheaper than a ninth.

## 12 · The compositor was not the problem

§11 concluded that the hue clause was a compositing failure: the palette was
right and 262k additively blended tracers were averaging it away. `?comp=1`
tests that directly — depth test and depth write, so the nearest tracer keeps a
pixel instead of everything summing.

**It changed 96% of the pixels and 0% of the hue distribution.**

| | slab | slab + depth rejection |
|---|---|---|
| pixels differing between the two | — | 96.3% |
| worst channel delta | — | 141/255 |
| hue peak (linear path, a = 0.7) | 260° at 76.5% | 260° at **74.2%** |
| hue peak (N-body, a = 0.45) | 210° at 53.3% | 210° at **53.2%** |

That is as clean a refutation as this project is likely to get. Rejecting
almost every tracer that was being summed leaves the hue histogram where it
was, so the tracers being rejected had *the same hue as the ones kept* — which
is exactly what a thin slab guarantees. The slab had already fixed the
depth-averaging problem in §10; §11 diagnosed a cause that was no longer there.

### What it actually is

The mass-weighted divergence field is **unimodal**. Its quantiles say so —
p05 −1.01, p50 −0.25, p95 +0.36 at D = 0.52 — and a strictly monotone transfer
of a unimodal scalar produces one dominant hue with tails, at every epoch. At
a = 0.45 that peak sits at 210°; by a = 0.7, with structure collapsing, it has
moved to 260° and grown to 76%, which is not a defect but a correct report that
by then almost everything is falling inward.

Four *modes* in a pixel histogram would need four independent physical channels
driving hue. §M1 provides one — divergence — plus virialization as a second,
which is precisely the achromatic cream family the gate already counts. Two
channels, two families.

### So the clause needs a decision, not another commit

§M1 asks for *"≥4 distinguishable hue families"*; §8 axis 6 asks for *"≤3 hue
families plus one accent."* Together they pin it at exactly four. The
disagreement is about what a *family* is:

- **As four modes in a pixel-hue histogram** — the operationalisation in
  `tools/gate.js` — it is unreachable from one monotone readout of one unimodal
  field, and nine iterations now say so from four directions.
- **As four hues a viewer can point at** — violet, blue, teal, amber, cream are
  all on screen, all selected by physics, all inside the luminance band. This is
  §9's option (3), and the frames support it.

The first reading demands a second independent physical channel in the hue —
which is a design change to what the scale *says*, not a rendering fix. The
second demands changing the measurement. Both are the human's call; neither is
a bug.

`?comp=1` stays, honestly labelled. It did not do what it was built for, it
costs nothing when off, and a frame where the nearest structure owns its pixels
is a defensible thing to have on a flag.

## 13 · Option B, built — the second channel

The decision in §12 went to option B: give hue a second independent physical
channel rather than change what the measurement means. `?web=1`, default-off.

### The channel

The eigenvalues of B = I + D·M are the stretch factors of the three principal
axes of a Lagrangian element. Counting how many have contracted past a
threshold is the standard classification of cosmic structure (Hahn et al. 2007;
Forero-Romero et al. 2009):

| collapsing axes | structure |
|---|---|
| 0 | void |
| 1 | sheet / wall |
| 2 | filament |
| 3 | knot |

This is not a recolouring of the same number. Divergence is the **trace** of the
flow; the classification is its **signature**. Two elements can share a
divergence and be a sheet and a filament, and every published image of the
cosmic web is drawn in these four classes.

The threshold is what makes it evolve. At λ_th = 0 the sign of λ never changes —
D scales the eigenvalues but cannot flip them — so every point would carry one
class forever, which is a stencil rather than a web. Requiring an axis to have
contracted by 20% makes the class a function of D, and the census moves as it
should: void 49.5% → 12.4% and knot 0.1% → 4.2% between D = 0.25 and D = 1.4.

**Two to three.** The channel is real and it moved the clause. It did not reach

### What blocks the fourth — and it is §11's diagnosis, arriving late

Two of the four classes barely reach the frame:

- **Voids are sparse by construction.** A void is a region that has *few
  particles*; its tracers spread over a large Eulerian volume, so the amber
  family lands at 0.9% of lit pixels however bright each tracer is.
- **Knots are rare.** 2.5% of elements at D = 0.7, 4.2% at D = 1.4.

And the frame is **40.5% achromatic**. Narrowing the class transitions and
tightening the virialization stop moved that number not at all, which rules out
both as the cause and leaves one: additive blending of tracers that now
genuinely differ in hue sums to a desaturated mean.

§11 diagnosed exactly this and §12 refuted it — *"it changed 96% of the pixels
and 0% of the hue distribution"*. Both were right. The refutation held because
the hue field was **smooth**: a mean of neighbouring hues that are nearly equal
is that hue. Giving hue a discrete second channel is what makes the averaging
visible, and it is now the binding constraint.

So the fourth family needs the compositing fixed properly — a nearest-tracer or
dominant-class resolve rather than a sum — which is a rendering change of its
own size, not a palette tweak. `?comp=1`'s depth rejection is not enough: it
rejects whole tracers, but each surviving tracer is a soft round point whose
additive falloff still overlaps its neighbours.

The N-body path is also still on the divergence ramp. Its density comes from the
simulated field rather than the tensor, so the classification needs either a
tidal-tensor pass over that field or the Zel'dovich tensor evaluated at each
particle's Lagrangian position — which is recoverable, `nbody.js`'s IC shader
derives it from the particle index at line 58, and the display shader already
runs the same 64-mode loop. Named so it is a known next step and not a gap.
