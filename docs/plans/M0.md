## 2 · Design notes worth arguing with

**The route is a property of the seed, not of the tooling.** Both instruments
resolve their itinerary in-page through `hash`, `galaxyParams` and
`systemParams` — the same pure generators the universe uses — rather than
hardcoding a list of deep links. A hardcoded route would keep working after a
generator drifted; a derived one changes, loudly, which is the alarm §2.3
wants. The cost is that a legitimate generator change reshuffles the capture
set and has to be re-baselined deliberately.

**Settling is counted in frames, not milliseconds.** A slow machine takes
longer and shoots the same frame. This is the single reason the capture set is
comparable between a laptop and CI at all.

**Adaptive resolution is pinned during a bench run.** §11 lists mid-frame
adaptive quality as a known trap. During a *measured* flight it is worse than a
trap: the controller in `main.js` lowers DPR when frames get slow, so an
unpinned run measures the resolution controller converging and reports it as
renderer performance. `?bench=1` sets `app._benchPinned` and the controller
stands down. (The controller's presence in normal runs is itself a §11
finding — see §3.)

**GPU memory is accounted, not queried.** WebGL exposes no memory query. The
harness patches the context before the renderer is built and tracks
textures, buffers and renderbuffers minus deletes. It is an estimate and the
JSON carries a `method` field saying so, rather than presenting a number with
implied authority. Installed only under `?bench=1`, so normal runs pay nothing.

**The HUD is hidden before every capture.** §8 axis 7 asks whether the frame
survives without chrome; making that structural means the critic answers it
from the frame instead of from memory.

**A software rasteriser is reported, never hidden.** §M0 requires a real GPU
because SwiftShader produces a full, well-formed, worthless perf JSON. Every
report carries `device.renderer` and stamps `gateValid: false` on sight of
SwiftShader or llvmpipe, and `capture.js` prints a warning when no tier ran on
real silicon.

## 3 · Audit: what the instrument found on its first pass

M0 is where the codebase is measured against the constitution for the first
time. Three findings. **None is M0's to fix** — each is recorded here and
routed, per §3's instruction not to re-litigate mid-build.

### 3.1 · The whole universe currently renders through ACES · → M2

`main.js` sets `renderer.toneMapping = THREE.ACESFilmicToneMapping`, and
`post.js` ends its chain on `OutputPass`, which applies it. §9.4 specifies a
rational curve — `x(0.36x + 0.42) / (x(0.34x + 0.66) + 0.11)` — and says *"Not
ACES. Not Reinhard."* v1 said "Never ACES" too, so this predates the rewrite
and was not caught by either.

This is the largest single gap between the constitution and the pixels. It is
M2 work (§6 M2 says port §9.2 and §9.3 *first*, because they change every
subsequent frame; the print is the same argument), and it interacts with §2.8's
vacuum/atmosphere split, which is also unbuilt — `post.js` has one grade path
with a per-world lift, not two regimes cross-fading on atmospheric entry.

Recorded, not fixed: changing the tonemap re-grades every existing capture in
`docs/screenshots/`, which is a deliberate act with a re-shoot attached.

### 3.2 · Adaptive resolution moves mid-flight · → §5 quality table

`main.js` steps DPR up and down every 70 frames against a frame-time average.
§11: *"Adaptive quality mid-frame. Set once at init. Live changes pump
visibly."* The floor logic already concedes the point — it holds resolution up
during flown sequences *"which is exactly when it must look like cinema."*

The real fix is §5's four-row quality table (one array indexed by tier, every
knob in the row), which does not exist yet. Pinning DPR without it would just
trade pumping for a fixed wrong answer on low-end hardware. Route it with the
table; until then, `?bench=1` pins it so the measurements are clean.

### 3.3 · The universe is deterministic; the frame is not · → M0.1, cheap

17 modules call `Math.random()` — but every call site is a *transient particle
or agent*: petal spawn, waterfall spray, rain, lightning timing, orbital debris,
boid headings, city traffic. Nothing writes persistent world state. Terrain,
biomes, settlements, names and orbits all run through `src/rng.js`.

So §2.3 holds as written — no generation path leaks — and shareable URLs are
safe. But a consequence lands on the workflow: **two captures of the same URL
are not pixel-identical**, which means §7.3's offline-validation method (*"a
pixel diff against the GPU output — ≥97% of pixels within 2/255"*) cannot be
run on any frame containing particles, and §7.7's "re-shoot and re-score every
previous milestone" can only be scored by eye.

Recommended: route transient spawns through a per-system `RNG` seeded from the
world seed. It is mechanical, it touches 17 files, and it belongs in its own
commit with its own review rather than inside M0's tooling.

## 4 · Risks, and what is not proven

**⚠ This container has no GPU.** Chromium here runs ANGLE-over-SwiftShader. The
instruments run end to end and the *shapes* in the perf JSON are real, but
every number is a software-rasteriser number and every report in
`docs/captures/M0/` is stamped `gateValid: false`. **M0's gate is therefore not
met and is not claimed.** It needs one run on desktop-reference silicon.

**⚠ "Perf JSON for all three tiers" is honoured in the only sense available.**
`TIERS` maps the three rows of §5 onto viewport and DPR, because those are the
only quality knobs that exist today. §5's four-row table — every knob in one
row, one row reconfigures the renderer — is unbuilt, so a tier is currently a
*device*, not a *configuration*. Both `lib.js` and `tools/README.md` say so
where a reader will trip over it. Two ways to go:

1. Ship M0 with device-tiers and build the quality table as M2's first act
   (it is a §5 requirement and M2 is the first milestone that spends frames).
2. Hold M0 open and build the table now.

This is a real fork and it is the human's call. Recommendation: **(1)** — the
table wants real knobs to index, and M2 is where the knobs get built. Nothing
in M1 needs it.

**Other risks.**

| Risk | Mitigation |
|---|---|
| Capture route reshuffles when a generator changes | Intended (§2.3 alarm). Manifest records the resolved seeds per run, so a diff shows what moved. |
| Bench masks a real regression by pinning DPR | Pinning is bench-only. Normal runs keep the current behaviour until §3.2 is resolved. |
| GPU-memory estimate drifts from the driver's real figure | Labelled `method: tracked GL allocations minus deletes`. Compare it to itself across runs, not to a vendor tool. |
| Playwright global install rots | `lib.js` fails with the one-line fix instead of a resolution stack. No manifest, no lockfile, no build step (§2.2). |
| 20-minute bench timeout too tight on low tier | Configurable in `capture.js`; only reachable on software rasterisers. |

**Rollback.** Every instrument is additive and default-off. `git revert` of the
tooling commit removes `tools/`, `src/bench.js` and four hook lines in
`main.js`, and the universe is exactly as it was. The meteor removal is a
separate concern and reverting it would re-violate §4.

**Budgets at risk: none.** No instrument runs unless a URL parameter asks for
it. The one always-on change is a null guard on the splash timer.
